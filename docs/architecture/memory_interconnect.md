# Memory Interconnect

## 1. Overview

The `memory_interconnect` is the memory-mapped routing block between the RV32I CPU and system peripherals. It examines the CPU address and routes each transaction to the correct device.

```text
RV32I CPU
    |
    v
Memory Interconnect
    |
    +----> Data RAM       0x0000_0000 - 0x0000_0FFF
    |
    +----> SHA-256       0x1000_0000 - 0x1000_00FF
```

The SHA-256 interface is reserved for the next project phase.

## 2. Why This Block Is Required

The original RV32I datapath contained the data-memory instance directly. That was suitable for standalone CPU verification, but it made adding memory-mapped peripherals unnecessarily difficult.

The datapath was therefore changed to expose:

```text
mem_address
mem_write_data
mem_read
mem_write
mem_funct3
mem_read_data
```

The interconnect separates the CPU from individual memory-mapped devices.

This allows:
- the CPU to remain independent of peripheral implementation;
- additional peripherals to be added through address decoding;
- the SHA-256 accelerator to be accessed using normal load/store instructions.

## 3. Address Map

| Address Range | Device |
|---|---|
| `0x0000_0000 – 0x0000_0FFF` | Data RAM |
| `0x1000_0000 – 0x1000_00FF` | SHA-256 Accelerator |
| `0x2000_0000 – 0x2000_00FF` | Reserved for future peripherals |

Unsupported addresses generate no device request and return zero on reads.

## 4. CPU-Side Interface

| Signal | Direction | Description |
|---|---|---|
| `cpu_address` | Input | CPU-generated address |
| `cpu_write_data` | Input | Store data |
| `cpu_read` | Input | Load/read request |
| `cpu_write` | Input | Store/write request |
| `cpu_funct3` | Input | RV32I memory-operation type |
| `cpu_read_data` | Output | Read data returned to CPU |

## 5. Data RAM Interface

| Signal | Direction | Description |
|---|---|---|
| `ram_read` | Output | RAM read enable |
| `ram_write` | Output | RAM write enable |
| `ram_address` | Output | RAM address |
| `ram_write_data` | Output | RAM write data |
| `ram_funct3` | Output | Load/store type |
| `ram_read_data` | Input | RAM read response |

A RAM request is generated only when the CPU address is inside the RAM region:

```verilog
ram_read  = cpu_read  && ram_select;
ram_write = cpu_write && ram_select;
```

## 6. SHA-256 Interface

| Signal | Direction | Description |
|---|---|---|
| `sha_read` | Output | SHA-256 read request |
| `sha_write` | Output | SHA-256 write request |
| `sha_address` | Output | SHA-256 register address |
| `sha_write_data` | Output | Data supplied to SHA-256 |
| `sha_funct3` | Output | RV32I access type |
| `sha_read_data` | Input | SHA-256 read response |

The accelerator is not yet implemented. During the current CPU integration, `sha_read_data` is tied to zero.

## 7. Address Decoding

Device-select signals are generated by comparing the CPU address against the defined ranges:

```verilog
ram_select =
    (cpu_address >= RAM_BASE) &&
    (cpu_address <= RAM_END);

sha_select =
    (cpu_address >= SHA_BASE) &&
    (cpu_address <= SHA_END);
```

Only the selected device receives the read/write enable.

## 8. Read-Data Multiplexing

The CPU has one read-data input, while several devices can provide responses. The interconnect therefore selects the response from the addressed device:

```verilog
cpu_read_data =
    ram_select ? ram_read_data :
    sha_select ? sha_read_data :
    32'b0;
```

Thus:

```text
RAM address  -> RAM response -> CPU
SHA address  -> SHA response -> CPU
Other        -> zero         -> CPU
```

## 9. Combinational Design

The interconnect is purely combinational. It contains address comparisons, request gating, signal routing, and read-data multiplexing.

It has no clock, reset, or storage elements. State remains inside the connected devices.

## 10. CPU Integration

After integration the architecture is:

```text
RV32I CPU
    |
    v
Memory Interface
    |
    v
Memory Interconnect
    |
    +----> Data RAM
    |
    +----> SHA-256 address space
```

The CPU continues to generate the same memory requests; the interconnect determines where they are routed.

## 11. Design Considerations

### Device isolation

A RAM transaction must not activate the SHA-256 interface, and a SHA-256 transaction must not activate RAM.

### Unsupported addresses

Unmapped addresses generate no device request. Reads from them return zero.

### Extensibility

A new peripheral can be added by defining a new address range, select signal, device interface, and read-data multiplexer input without changing the CPU datapath.

## 12. Result

The data-memory architecture has been upgraded from a CPU-local memory to a memory-mapped subsystem:

```text
RV32I CPU
    |
    v
Memory Interface
    |
    v
Memory Interconnect
    |
    +----> Data RAM
    |
    +----> SHA-256 address space
```

The next major block is the SHA-256 accelerator.
